### 4. Architecture Overview
Include the 4-container diagram from spec §3 (ASCII or mermaid).

### 5. Pipeline Stages
Brief description of each stage: AmbiguityDetector → QueryClassifier → SQLGenerator → SQLExecutor (ReAct) → ResultSynthesizer.

### 6. Architecture Decision Table (required: all 10 from spec §9)

| Decision | Why | Tradeoff |
|---|---|---|
| DIN-SQL stage decomposition | Token budget management per stage; enables two-model strategy | More code; each stage is a failure point |
| CREATE TABLE over natural language schema | Forces correct column reference and type awareness | Slightly more verbose in prompt |
| Date normalization at ingestion (not in SQL) | Source M/D/YYYY; fixed-position substr() fails for 48% of rows | Requires Python preprocessing step |
| ReAct over fixed retry | Detects semantic failures (0 rows, wrong cardinality) that syntax retry misses | More complex; 2× latency per correction step |
| Rule-based AmbiguityDetector | Zero latency; LLM call adds 20–30s before SQL generation | Coverage is finite; open-domain queries may not resolve |
| Keyword heuristic QueryClassifier | Fires for 60–70% of questions at near-zero cost | May misclassify edge cases |
| SQLite over Postgres | Simplest possible db for demo scope; no infrastructure overhead | Not production-grade for concurrency |
| Four containers over monolith | Each service independently scalable; clear separation of concerns | More orchestration complexity |
| Two-model strategy (14B SQL + 32B synthesis) | Task-matched: SQL needs code precision, synthesis needs narrative reasoning | 29 GB download; synthesis 2–5 min |
| Structural few-shot examples | Demonstrates expected SQL shape per class without overfitting to specific values | One example per class may not cover all variations |

### 7. Evaluation Harness
- 12 POS-domain test cases across 4 query classes
- Two-layer: SQL structural check + LLM-as-judge on narrative
- **Final-pass gate, not CI regression. Full run: 90–120 min on GPU.**
- Run: `docker compose exec nlp python -m nlp.eval.harness`

### 8. Scale-Out (3 scenarios from spec §9)
1. **More tables / larger schema:** retrieval-augmented SchemaLinker (ChromaDB/pgvector). Pipeline code unchanged.
2. **More data:** SQLite → PostgreSQL. `db` service interface (`POST /execute`) unchanged.
3. **High traffic:** multiple `nlp` replicas + Redis job queue for async processing.

### 9. Production Delta
What would change for a real Nivii deployment (from spec §9):
- Automated schema enrichment
- LLM-path AmbiguityDetector
- Kubernetes per-client deployment
- Continuous evaluation pipeline
- Synthesis plausibility filter
- CHASE-SQL candidate consistency

### 10. Limitations
- Local model SQL reliability on complex queries
- Latency on CPU-only machines (see §3)
- Dataset scope: 60 days (Sep–Nov 2024); annual queries return partial results
- AmbiguityDetector rule coverage is finite
- Eval harness is final-pass gate, not continuous regression

### 11. Dataset
- 24,212 rows, 9 columns, 68 products, 11,771 tickets, 9 waiters
- 60 days: Sep 21 – Nov 20, 2024
- Revenue: Sep 34.3M ARS · Oct 110.6M ARS · Nov 70.3M ARS ARS
- `data.csv` is not committed — provide it at repo root before `docker compose up`
