## §2. Shared Contracts

### Types / Interfaces (T4 owns these — T5, T6 consume them)

```python
# nlp/pipeline/sql_executor.py
from enum import Enum
from dataclasses import dataclass

class Action(Enum):
    ACCEPT = "accept"
    REFINE = "refine"

@dataclass
class ObservationResult:
    action: Action
    message: str

@dataclass
class ExecutionResult:
    success: bool
    data: list[dict] | None = None
    columns: list[str] | None = None
    sql: str = ""
    steps_taken: int = 0
    failure_reason: str | None = None
```

```python
# nlp/pipeline/pipeline.py
from dataclasses import dataclass

@dataclass
class PipelineResult:
    question: str
    resolved_question: str
    interpretations: list[str]
    query_class: str
    sql: str
    execution: ExecutionResult
    narrative: str | None
    run_id: str
    total_latency_ms: int
```

**CRITICAL:** `PipelineResult` field names are consumed by:
- T5 Jinja2 template: `result.narrative`, `result.sql`, `result.execution.success`, `result.execution.data`, `result.execution.columns`, `result.interpretations`, `result.query_class`, `result.resolved_question`, `result.execution.steps_taken`
- T6 eval harness: `pipeline_result.sql`, `pipeline_result.execution.data`, `pipeline_result.narrative`, `pipeline_result.query_class`, `pipeline_result.total_latency_ms`, `pipeline_result.execution.steps_taken`, `pipeline_result.execution.failure_reason`

Do not rename fields. **Serialization ownership:**
- **HTTP JSON** (`nlp/main.py POST /query`): T4 uses `dataclasses.asdict(result)` before returning. `asdict` recurses into nested dataclasses automatically.
- **Jinja2 template** (T5): T5 calls `nlp POST /query` and gets back plain JSON via `response.json()` — already a dict. T5's template receives a dict; Jinja2 resolves `{{ result.narrative }}` as dict key access. **T5 never sees the dataclass object.** No `asdict()` in T5.

### Error Envelope (db API — T4 parses this in `_try_execute`)

| db Endpoint | Success shape | Error shape |

| `POST /execute` | `{"columns": [...], "rows": [[...], ...], "row_count": N}` | `{"error": "message", "sql": "..."}` |

`_try_execute` must parse these exact field names. Check for `"error"` key presence to distinguish success from failure.

**Kill criteria:**
- HALT if `_observe_result` uses string sentinel (`"Accept." in observation`) — must use `ObservationResult` with `Action` enum
- HALT if `synthesize` calls the LLM when `result.success is False` or `result.data` is falsy (empty list or None) — guard is mandatory
- HALT if `build_refinement_prompt` is a stub returning an empty string — must be the full prompt from spec §5.6
- HALT if `execute_react` default `max_steps` is not 4
- HALT if `_build_synthesis_prompt` does not truncate result data to `data[:10]` before LLM injection
- HALT if `Pipeline.run()` calls `synthesize` outside the `if execution.success and execution.data` guard
- HALT if `nlp/main.py` returns HTTP 500 for any handled pipeline error — must return HTTP 200 with `{"error": "..."}` body
- HALT if `ResultSynthesizer.synthesize` uses `temperature=0.0` — must use `temperature=0.3` (narrative quality requires slight randomness)

**Risks & mitigations:**
- `_try_execute` calls the db over HTTP using `httpx`. Use `httpx.post(f"{db_url}/execute", json={"sql": sql}, timeout=30.0)`. On `httpx.HTTPError` or `httpx.ConnectError`, return `ExecutionResult(success=False, failure_reason="db unreachable: <error>")` — do not raise.
- The synthesis temperature is 0.3 per spec — do not change without documenting rationale in the decision log.
- **Serialization:** In `nlp/main.py`, use `dataclasses.asdict(result)` when returning the JSON response from `POST /query`. This converts `PipelineResult` and all nested dataclasses (including `ExecutionResult`) to plain dicts recursively. Do **not** pass the raw dataclass to `JSONResponse` — it is not JSON-serializable directly. The Jinja2 template in T5 is **not** T4's concern: T5 receives the already-serialized JSON dict from the HTTP call and Jinja2 handles dict key access natively.

## Key Implementation Reference

### `sql_executor.py` — ReAct loop (verbatim from spec §5.6)

```python
def execute_react(self, sql, question, linked_schema, max_steps=4) -> ExecutionResult:
    for step in range(max_steps):
        result = self._try_execute(sql)
        if not result.success:
            obs = ObservationResult(action=Action.REFINE, message=f"SQL error: {result.error}")
        else:
            obs = self._observe_result(question, sql, result)
        self._log_step(step, sql, obs)
        if obs.action == Action.ACCEPT:
            return ExecutionResult(success=True, data=result.data, columns=result.columns, sql=sql, steps_taken=step + 1)
        sql = self.sql_generator.refine(sql, obs.message, linked_schema)
    return ExecutionResult(success=False, sql=sql, steps_taken=max_steps, failure_reason="max steps reached without successful result")

def _observe_result(self, question, sql, result) -> ObservationResult:
    row_count = len(result.data)
    if row_count == 0:
        return ObservationResult(action=Action.REFINE, message="Query returned 0 rows. ...")
    if row_count > 10_000:
        return ObservationResult(action=Action.REFINE, message=f"Query returned {row_count} rows. ...")
    scalar_indicators = ["total", "average", "how many", "count", "sum", "most", "top"]
    expects_scalar = any(w in question.lower() for w in scalar_indicators)
    if expects_scalar and row_count > 50:
        return ObservationResult(action=Action.REFINE, message=f"Question implies aggregated result but got {row_count} rows. ...")
    return ObservationResult(action=Action.ACCEPT, message="Result shape matches question intent.")
```

See spec §5.6 for full message strings in `_observe_result`.

### `build_refinement_prompt` — verbatim from spec §5.6

```python
def build_refinement_prompt(original_sql, observation, schema, question) -> str:
    return f"""You are correcting a SQL query that failed or produced a bad result.

Schema:
{schema}

Original question: {question}

Attempted SQL:
{original_sql}

Problem observed:
{observation}

Instructions:
- Fix only the specific problem described above.
- Keep all correct parts of the original query unchanged.
- Do not add columns, tables, or logic not needed to fix the stated problem.
- Common fixes for '0 rows': check WHERE clause values match actual data
  (week_day values: Monday/Tuesday/Wednesday/Thursday/Friday/Saturday/Sunday;
   product names are case-sensitive exact strings).
- Common fixes for 'too many rows': add GROUP BY, ORDER BY + LIMIT, or a WHERE filter.
- Common fixes for SQL errors: check column names against the schema above.

Return only the corrected SQL query. No explanation. No markdown fences."""
```

### `pipeline.py` — orchestration (spec §5.9)

```python
def run(self, question: str) -> PipelineResult:
    run_id = datetime.utcnow().isoformat()
    t0 = time.time()
    resolved = self.ambiguity_detector.detect_and_resolve(question, self.domain)
    linked_schema = self.schema_linker.link(resolved.resolved)
    query_class, cls_method = self.query_classifier.classify(resolved.resolved, self.llm_client)
    self._log(run_id, "classifier", {"class": query_class.value, "method": cls_method})
    sql = self.sql_generator.generate_sql(resolved, linked_schema, query_class, self.kpis, self.llm_client)
    execution = self.sql_executor.execute_react(sql, resolved.resolved, linked_schema)
    narrative = None
    if execution.success and execution.data:
        narrative = self.result_synthesizer.synthesize(question=question, result=execution, interpretations=resolved.interpretations_applied)
    return PipelineResult(
        question=question, resolved_question=resolved.resolved,
        interpretations=resolved.interpretations_applied, query_class=query_class.value,
        sql=execution.sql, execution=execution, narrative=narrative,
        run_id=run_id, total_latency_ms=int((time.time() - t0) * 1000),
    )
```
